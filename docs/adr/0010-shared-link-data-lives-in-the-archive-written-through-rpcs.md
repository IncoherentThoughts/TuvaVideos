# Shared link data lives in the archive's Supabase project and the browser writes it through RPCs; the companion stays Supabase-blind except for Sync

The v1 app was single-user and offline: SQLite the only store, the network touched only by one-off scripts (`docs/spec.md` §1). Sharing the link data with a handful of collaborators needs a store outside any one machine. Decided (#95, 2026-10-17; the parts from #83, #84, #86, #90, #91 and #92): the Shared tables live in the **Tuvan Lyrics Archive's own Supabase project**, in `public` with a `video_` prefix, so every safety net the archive already has (anon revokes, default privileges, pgTAP, the live RLS snapshot) covers them from the first migration; the **Preact app in the browser** signs in with the archive account through supabase-js, reads with the public key under RLS and writes only through `write_*`, `elevate_*` and `set_song_exposure` functions in the archive's ADR-0011 shape, each carrying its edit history in the same transaction; and the **Bun companion** holds the Local copy for the Player, search and the TV, learns of the browser's writes through `POST /api/cache/apply`, and touches Supabase only during **Sync**, with the access token the browser hands it for that one call and never stores. A token-free **Session record** in the companion is the machine's fact of who is signed in; the browser's session is what carries the token.

Alternatives rejected: a separate Supabase project for the videos (would duplicate the accounts and put the archive's Songs behind a second RLS surface with no foreign keys); a dedicated `videos` schema (outside every archive safety net and needing an "Exposed schemas" step, `.schema()` on every call and Prisma multi-schema); the companion as the Supabase client (it would have to hold and refresh the user's token, and single-use rotating refresh tokens make a second refresher a session killer, #84); the companion verifying tokens against the project's JWKS (#84's proposal, dropped in #91: Supabase verifies the token when it is used, and the companion needs no long-lived identity of its own); Realtime (needs the watermark pull underneath anyway); and the edit history as a change feed (per field, lossy under CASCADE).

Consequences: the app now depends on the network for Sync and for every Shared write, with the Local copy keeping browsing and playback offline; the public key and project URL are committed in `src/shared/archive.ts` (RLS and the session are the gate, as for the archive's own public site); RLS reading the console-only `video_access` grant is the only real permission check, and every control in the app is courtesy; and the archive's conventions bind every schema change here (numbered migrations, pgTAP per function, snapshot refresh at the live apply). The v1 constraints stay in force for everything that is not Shared data: files, Copies, Roots, thumbnails and playback state never leave the machine.
