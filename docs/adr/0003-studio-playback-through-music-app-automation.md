# Studio playback drives Music.app through Apple events, not MusicKit or in-browser audio

Studio playback (hearing the studio recording of what a Video performs) sends JXA commands to Music.app through a resident `osascript` child owned by the server, addressing tracks by Music.app's persistent ID and steering play, pause, seek and loop from the browser by command and 1–4 Hz polling. The alternatives were playing the files in a browser `<audio>` element (impossible: 925 of 1362 downloaded tracks are FairPlay `.m4p` and 1638 more are stream-only, so under a third of the library is a plain file) and MusicKit JS, which plays inside the tab but needs a paid Apple Developer Program membership, a signed token rotated every six months, a network connection, and a second id namespace (`i.…`) that does not cover the uploaded and matched mp3s. Consequence: audio comes out of Music.app, not the tab, so the browser can only mirror its state with ~0.4 s command latency hidden by the resident child; every control the Player offers in Studio mode (space, arrows, scrub, A-B loop) is a command plus a poll rather than an element property; the app depends on a one-time macOS Automation consent and on Music.app's persistent IDs, which survive restarts but not a library rebuild (handled by re-matching). Decided in [issue #15](https://github.com/IncoherentThoughts/TuvaVideos/issues/15) on the research in #4.
