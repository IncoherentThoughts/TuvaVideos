# Playback is a plain browser `<video>` over a Range-capable localhost server, not mpv

The Player is a `<video src>` element pointed at the app's own server, which serves each Copy's file with HTTP Range support; the app's mpv-style keys are reimplemented on that element. The alternatives were mpv driven over JSON IPC with its window beside the browser (true mpv behaviour, but two windows, no in-page overlay for chapters, lyrics or OSD, and a second process lifecycle) and MediaSource with a demuxer (rejected because Chromium's MSE refuses Matroska, which is 59% of the library). Research in #3 showed 1,136 of 1,137 files play as-is with 16–175 ms seeks, and the prototype in #10 confirmed key seeks feel instant up to 1080p30 and that every binding reaches the page in Chromium and Brave. Consequence: the handful of files Chromium cannot play get a one-time cached Fallback (audio transcode or Cues remux) decided by ffprobe at scan time, never a live pipe; playback behaviour is bounded by Chromium's decoders (an exact seek decodes from the previous keyframe, ~5 s back in this library, so it shows after ~0.3–0.6 s; since 2026-10-13 the bar and the plain arrows snap to a per-Copy keyframe index instead, as mpv does, spec §4.1), and swapping to mpv later would mean rebuilding the Now-playing screen around an external window. Decided in [issue #10](https://github.com/IncoherentThoughts/TuvaVideos/issues/10) and ratified in [issue #14](https://github.com/IncoherentThoughts/TuvaVideos/issues/14).
