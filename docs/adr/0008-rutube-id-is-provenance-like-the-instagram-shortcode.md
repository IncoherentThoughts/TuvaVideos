# A Rutube id is provenance like the Instagram shortcode, not identity

The library holds 34 Copies downloaded from rutube.ru by `scripts/download-rutube.sh`, which names them `… [rutube-<32-hex id>].<ext>`. Until now `filename.ts` knew no Rutube suffix: those Videos were known by content hash only, five titles still carried the suffix, and the Mirror's 34 Rutube performance URLs (every one of which matches a file in the library) suggested nothing, because scan defaults joined on `youtube_id` alone.

Decided (#104, 2026-10-17): the Rutube id is kept in `video.rutube_id`, non-unique, parsed from the filename suffix like `[instagram-<shortcode>]` and backfilled from Copy filenames by migration, with the suffix stripped from titles. The Video's identity stays the content hash exactly as ADR-0005 settles for Instagram: a new id-less file whose bytes match no Video but whose Rutube id is known joins that Video as another Copy, a hash match that lacks the id picks up the file's, and an entry-only delete tombstones the hash, not the id. Rutube serves HLS, so a re-download rarely yields the same bytes, which is the Instagram case again. The column is Shared (amending #89's identity line), shown and linked as `https://rutube.ru/video/<id>/` wherever the YouTube id and shortcode are, and a reconciliation key at sign-in in the scan's order: YouTube id, content hash, then shortcode or Rutube id. Import parses the id out of rutube.ru performance URLs into `archive_performance.rutube_id` and the performance defaults match on either id.

Making it an identity like `youtube_id` was rejected for the reasons in ADR-0005: migrating rows off their hash, a third tombstone key and a uniqueness rule that the duplicate cleanup works against, for no gain. Replacing the per-platform columns with a general `source_kind` + `source_id` was deferred: three columns stay until the in-app downloader effort decides with real platforms in hand.
