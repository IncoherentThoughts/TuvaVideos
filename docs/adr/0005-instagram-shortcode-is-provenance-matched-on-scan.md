# An Instagram shortcode is provenance, not identity, but a new file carrying a known one joins that Video

yt-dlp names Instagram downloads `… [instagram-<shortcode>].<ext>`. Until now the shortcode was only stripped from the title, so an Instagram Video had no recorded source and was known only by its content hash. It is now kept in `video.instagram_id` (backfilled from Copy filenames by migration 0013) and shown and linked like the YouTube id. The Video's identity stays the content hash: `deleted_video` and the thumbnail cache are keyed as before, and the column is not unique, so while a duplicate is being cleaned up the keeper can be given the shortcode by hand before the other Video is deleted. The one place the shortcode acts like an identity is the scan: a new id-less file whose bytes match no Video but whose shortcode does becomes another Copy of that Video (the lowest id when several share it), since re-downloading a post rarely gives the same bytes. A Video found by content hash that lacks a shortcode picks up the file's. The alternative, making the shortcode a full identity like `youtube_id`, would have meant migrating existing rows off `content_hash`, a third tombstone key, and a uniqueness rule that the duplicate cleanup works against. Consequence: deleting an Instagram Video "entry only" tombstones its content hash, not its shortcode, so a different download of the same post can still come back as a new Video. Decided with the user in the duplicate-cleanup follow-up, 2026-10-15.
